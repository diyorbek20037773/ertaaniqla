# ADR-0002 — DMED (national e-health platform) integration: open item

- Status: **open** (2026-09-15) — waiting for the client
- Deciders: sole developer; client (Project Office) must answer

## Context

The TZ budget (§IV) says only "Уточнить стоимость DMED". Scope of any DMED integration or hosting
is undefined: it could mean (a) hosting the portal on DMED infrastructure, (b) pulling the list of
medical institutions from DMED, (c) publishing screening appointments through DMED, or (d) nothing.

## Decision (interim)

Do not design DMED out and do not build against a guessed API:

1. Institution and screening data are kept in **importable/exportable form**: `Institution`
   (`apps/directory`) has a CSV import command (`import_institutions`) and a CSV/JSON export
   (`export_institutions`); every record carries an optional `external_id` + `external_source`
   for a future DMED sync.
2. The site runs on its own VPS in Uzbekistan (spec §8); moving to DMED-hosted infrastructure
   is a compose-level change (same image).
3. Read-only Wagtail API v2 (`/api/v2/`) can be enabled without refactoring (spec §6) if DMED needs
   to consume content.

## Questions for the client

- Is DMED integration required for launch (August 2026)?
- If yes: which direction (import institutions / export content / hosting), and who provides API
  credentials and documentation?
- Is there a data-residency requirement beyond ЗРУ-547 that DMED enforces?

Update this ADR to *accepted* with the concrete scope once answered.
